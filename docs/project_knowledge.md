# 1. Project Overview

The project converts retro sound-chip music data, especially VGM data using YM2413/OPLL, into MIDI representations suitable for hardware synthesizers such as the Yamaha TX802.

The broader goal is not merely to produce MIDI that "sounds similar", but to preserve as much of the musical behavior encoded in the original chip data as practical.

The conversion pipeline currently conceptually follows:

```text
VGM
 ↓
chip register events
 ↓
intermediate segment representation
 ↓
musical/event interpretation
 ↓
MIDI
 ↓
hardware synthesizer (e.g. TX802)
```

The intermediate `segment` representation is important.

Do not bypass or excessively simplify this intermediate representation without understanding why it exists.

---

# 2. Core Design Philosophy

## 2.1 Equivalent output does not necessarily mean equivalent value

The project distinguishes between:

* producing the same audible result
* reproducing the same underlying musical/chip behavior
* preserving the historical characteristics of the source hardware

These are not necessarily the same goal.

A conversion can sound acceptable while losing important information encoded in the original register stream.

Therefore, optimization should not automatically favor the simplest MIDI representation.

---

# 3. VGM Is an Event Stream, Not a MIDI Score

A VGM contains register writes and timing information.

It should not immediately be interpreted as conventional musical notation.

Important information may exist in:

* key-on/key-off timing
* F-number changes
* instrument changes
* volume changes
* retrigger behavior
* pitch changes
* portamento-like behavior
* register-write ordering
* repeated writes that appear redundant from a purely musical perspective

Some apparently redundant events may actually matter.

Therefore:

> Do not aggressively merge or normalize events merely because they produce the same MIDI notes.

---

# 4. Segment Intermediate Representation

The project uses an intermediate `segment` representation between VGM and MIDI.

The purpose is to retain information that would otherwise be lost during direct conversion.

In particular, the segment representation has been used to mark/represent:

* retrigger
* legato
* note boundaries
* timing relationships
* volume-related information
* pitch/event information

The conversion process intentionally performs some semantic interpretation at this stage.

### Important design constraint

Do not "clean up" or over-compress the segment representation merely because the resulting MIDI becomes simpler.

A previous discussion established that excessive event integration can be musically incorrect.

For example, rhythmically sparse-looking data in the VGM may actually be the correct representation when listened to as VGM.

Therefore:

> Preserve event sparsity unless there is evidence that the sparsity is an artifact rather than meaningful source behavior.

---

# 5. Retrigger vs Legato

Retrigger and legato are intentionally distinguished.

A VGM stream can contain repeated pitch/note activity whose interpretation differs depending on whether the envelope should restart.

This distinction is important when converting to MIDI and subsequently to hardware synthesizers.

The project therefore marks retrigger/legato information during the intermediate representation stage rather than trying to reconstruct it only at the final MIDI stage.

Do not remove these distinctions simply because the MIDI note sequence looks equivalent.

---

# 6. Domino / MIDI Controller Behavior

The Yamaha TX802 workflow has involved comparing MIDI generated by the project with MIDI playback through Domino.

Domino appears to perform sophisticated restoration/processing of MIDI control changes/macros.

One important observation was:

> Domino's handling/restoration of CC-related information can make playback behavior significantly better.

This raised a broader design question:

Should controller restoration/normalization be treated as a general MIDI conversion requirement rather than something specific to Domino?

This remains a design question rather than a finalized specification.

Do not assume that all DAWs perform the same restoration/interpretation.

---

# 7. YM2413 / OPLL Volume Semantics

This is an important confirmed project detail.

For YM2413 OPLL:

```text
VOL = 0   → maximum volume
VOL = 15  → minimum / near silence
```

The direction is therefore inverted compared with many conventional volume representations.

Measured behavior was approximately:

```text
1 OPLL volume step ≈ 3 dB
```

The approximate range is therefore around:

```text
VOL 0  ≈ 0 dB
VOL 15 ≈ -45 dB
```

Do not accidentally interpret larger OPLL VOL values as louder.

This was a source of previous confusion and should be explicitly documented in code/comments where appropriate.

---

# 8. OPLL → TX802 Volume / Velocity Mapping

The project maps OPLL volume behavior to MIDI velocity for the TX802.

A naive linear mapping was found to be problematic.

In particular:

> Low-volume OPLL sounds can become excessively quiet when mapped directly/linearly to TX802 MIDI velocity.

This means that preserving the numerical volume ratio is not necessarily equivalent to preserving perceived or hardware playback behavior.

The current conceptual approach assumes TX802 Velocity Sensitivity = 7 and applies a non-linear mapping.

An earlier working mapping included approximately:

```text
OPLL VOL 0 → Velocity 98
OPLL VOL 1 → Velocity 86
OPLL VOL 2 → Velocity 76
OPLL VOL 3 → Velocity 68
OPLL VOL 4 → Velocity 60
OPLL VOL 5 → Velocity 52
OPLL VOL 6 → Velocity 44
OPLL VOL 7 → Velocity 38
OPLL VOL 8 → Velocity 32
OPLL VOL 9 → Velocity 26
```

This mapping should be treated as an experimental/hardware-oriented mapping, not as a mathematically proven equivalence.

Later values and the final implementation should be verified against the current source code and actual TX802 behavior.

---

# 9. Why Linear Volume Mapping Was Rejected

A straightforward mapping such as:

```text
OPLL VOL
     ↓
linear conversion
     ↓
MIDI velocity
```

does not reproduce the desired TX802 behavior satisfactorily.

The main observed problem was that low-volume notes become too weak.

Therefore, a nonlinear/exponential compensation was investigated.

One implementation experiment used:

* a base velocity range
* 15 OPLL volume steps
* additional lift for low OPLL volume values
* small random jitter

Example conceptual implementation:

```text
base_min = 55
base_max = 127
steps = 15

low-volume compensation:
VOL <= 3  → additional lift
VOL <= 6  → smaller additional lift

optional ±2 jitter
```

This is an experimental implementation.

The jitter in particular should not be considered a fundamental property of OPLL or TX802 unless independently justified.

---

# 10. Distinguish Three Different Things

When evaluating volume conversion, distinguish:

1. OPLL register semantics
2. TX802 MIDI velocity / Velocity Sensitivity behavior
3. human perceived loudness

These are related but not identical.

A conversion that preserves (1) numerically may fail at (3).

A conversion optimized for (3) may no longer represent (1) directly.

The project should explicitly document which objective is being optimized whenever a mapping is changed.

---

# 11. TX802 / FM Synthesis Context

The TX802 is being used as a real hardware target for MIDI generated from OPLL/VGM data.

The purpose is not simply to use any FM synth capable of receiving MIDI.

The TX802 is valuable because it provides actual Yamaha FM hardware behavior and makes it possible to compare:

```text
OPLL source
vs.
TX802 rendering
```

This makes real hardware testing an important part of the project.

Do not assume software FM emulation and TX802 hardware will produce identical results.

---

# 12. OPLL Presets → TX802

The project maps YM2413/OPLL preset voices to TX802-compatible FM voices.

This is inherently an approximation because the architectures differ.

Important architectural differences discussed include:

* OPLL uses a restricted voice architecture
* TX802 uses Yamaha 6-operator FM
* TX802's operator/waveform behavior differs from OPLL
* TX802 does not simply behave as an "expanded OPLL"

The goal is therefore not necessarily to reproduce every internal parameter identically.

Instead, the target is:

> preserve the characteristic timbre and musical identity of the OPLL voice while taking advantage of the TX802 architecture.

---

# 13. OPL3 / OPL4 Are Related but Separate Targets

The project also investigates OPL3/OPL4 conversion.

Do not assume that a solution optimized for TX802 automatically applies to OPL3/OPL4.

The project has considered:

```text
OPLL
 ↓
OPL3
```

and

```text
OPLL
 ↓
TX802
```

as separate target problems.

They may share analytical concepts, but their synthesis architectures and parameter mappings differ.

---

# 14. TX802 Waveform Constraint

The TX802 uses sine-wave operators in its normal FM synthesis architecture.

Do not assume that OPL3/OPLL waveform selection can be directly transferred to TX802.

When converting OPLL voices to TX802, waveform-related differences should be handled as part of the timbre approximation rather than by assuming direct waveform equivalence.

---

# 15. LFO / Envelope Considerations

The project has investigated TX802 LFO and envelope behavior because these affect whether an OPLL voice can be convincingly recreated.

When analyzing a voice, distinguish:

* operator frequency ratio
* detuning
* output level / TL
* envelope rates/levels
* feedback
* algorithm
* LFO
* pitch modulation
* amplitude modulation

Do not treat "FM parameters" as a single homogeneous parameter set.

---

# 16. OPLL Register Write Ordering

The order of YM2413 register writes matters.

A previously observed pattern was conceptually:

```text
KeyOn
→ FNUM
→ INST/VOL
```

and this can cause conversion problems if the converter assumes that MIDI note creation occurs only after all parameters have been established.

Do not assume that VGM register-write order corresponds directly to a clean MIDI Note On model.

The converter may need to reconstruct the effective state around a note event.

---

# 17. "Musically Correct" vs "Register Correct"

This distinction is fundamental.

There are at least three possible goals:

### A. Register correctness

Reproduce the original chip register state as accurately as possible.

### B. Musical correctness

Produce a MIDI sequence that represents the intended musical performance.

### C. Hardware-rendering correctness

Produce MIDI which causes the target hardware (TX802, OPL3, etc.) to sound as close as possible to the original.

These goals can conflict.

When changing an algorithm, state explicitly which one is being optimized.

---

# 18. Real Hardware Is Part of the Validation Loop

The project makes extensive use of actual hardware.

Relevant hardware includes:

* YM2413/OPLL-related systems
* MSX hardware
* TX802
* OPL3/OPL4-related systems
* S/PDIF audio interfaces
* UA-30 recording interfaces

Software playback is useful for development, but should not automatically be considered authoritative when the target is physical hardware.

Where possible:

```text
VGM
 ↓
reference playback
 ↓
recording

VGM
 ↓
conversion
 ↓
MIDI
 ↓
TX802
 ↓
recording

compare
```

should be used.

---

# 19. Do Not Overfit to One Song

A mapping that works on one VGM is not necessarily a general mapping.

Especially for:

* velocity
* envelope reconstruction
* retrigger behavior
* legato
* rhythm
* pitch interpretation

validate against multiple pieces.

A particularly good result on one track should be treated as evidence, not proof.

# 20. Experiments / Previously Problematic Approaches

## 20.1 Excessive event merging

Problem:

Aggressively merging/simplifying VGM events can make MIDI cleaner but can destroy meaningful rhythm/retrigger behavior.

Status:

Rejected as a general strategy.

---

## 20.2 Simple linear OPLL volume → MIDI velocity

Problem:

Low-volume notes became too quiet on TX802.

Status:

Rejected as the sole mapping strategy.

---

## 20.3 Treating VGM as conventional note data

Problem:

Register-level behavior and timing information can be lost.

Status:

Rejected.

Use an intermediate representation.

---

## 20.4 Assuming identical numerical parameters imply identical sound

Problem:

OPLL, OPL3 and TX802 have different synthesis architectures.

Status:

Rejected.

Parameter conversion must account for architecture.

---

# 21. Experimental Results vs Confirmed Facts

The project should maintain a strict distinction:

### Confirmed / relatively high confidence

* OPLL VOL direction is inverted: 0 loudest, 15 quietest.
* OPLL volume steps are approximately 3 dB.
* The VGM → segment → MIDI architecture is intentional.
* Retrigger/legato information is intentionally retained.
* Simple linear velocity mapping caused undesirable TX802 results.
* Real TX802 playback is being used as a validation target.

### Experimental

* Specific nonlinear velocity mappings.
* Low-volume compensation amounts.
* Random velocity jitter.
* Exact correspondence between OPLL volume and perceived TX802 loudness.
* Exact reconstruction of every OPLL preset on TX802.

### Open questions

* What is the mathematically/physically correct mapping between OPLL volume and TX802 velocity?
* How should TX802 Velocity Sensitivity be incorporated into the mapping?
* How much controller restoration should be performed during conversion?
* Which VGM event patterns represent intentional musical behavior versus driver implementation artifacts?
* How much of the OPLL envelope can/should be reconstructed on TX802?
* Which OPL3 algorithms provide the best perceptual approximation of specific OPLL voices?

# 22. Development Rules for Codex

When modifying this project:

1. Read the relevant knowledge/decision documents before making architectural changes.
2. Do not simplify the segment representation without explaining what information is being lost.
3. Do not replace hardware-derived observations with theoretical assumptions without testing.
4. Clearly distinguish measured facts, specifications, hypotheses and implementation heuristics.
5. Preserve retrigger/legato semantics unless there is a deliberate design decision to change them.
6. When modifying volume/velocity conversion, test both loud and quiet OPLL volume values.
7. Prefer reproducible tests over subjective claims where possible.
8. When possible, compare generated MIDI/VGM output against reference playback.
9. Avoid large refactors when a local fix is sufficient.
10. Before changing an established behavior, identify why the behavior exists.
11. Do not assume that "simpler MIDI" is "better MIDI".
12. Do not assume that numerical parameter equivalence implies sonic equivalence.
13. Record significant discoveries and rejected approaches so that future agents do not repeat the same experiments.

---

# 23. Preferred Development Workflow

For non-trivial changes:

```text
1. Inspect existing implementation
2. Identify relevant project knowledge
3. Explain current behavior
4. Form a hypothesis
5. Design a minimal experiment/test
6. Run the experiment
7. Compare results
8. Implement the change
9. Run regression tests
10. Record the result
```

Do not jump directly from a user request to a large rewrite.

---

# 24. Guiding Principle

The project is fundamentally about preserving information while crossing between different representations:

```text
chip register behavior
        ↓
musical interpretation
        ↓
MIDI representation
        ↓
different synthesis architecture
        ↓
audible result
```

Every conversion step potentially loses information.

The primary design question is therefore not:

> "How can we make this conversion simpler?"

but:

> "What information is being lost here, and is that loss intentional?"

This principle should guide architectural decisions.
